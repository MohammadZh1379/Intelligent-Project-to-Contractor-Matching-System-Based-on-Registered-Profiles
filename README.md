 ProjectEST

### Intelligent Company Matching and Ranking System Using Retrieval-Augmented Generation (RAG)

ProjectEST is an AI-powered application designed to retrieve, match, and rank company profiles based on user requirements, technical skills, and project descriptions. The system combines semantic search, keyword-based matching, and locally hosted language models to provide relevant company recommendations through a web interface.

The system is developed primarily for the **Persian language**: the user interface is Persian and right-to-left, queries are expected in Persian (English also works), and embeddings are generated with the multilingual `bge-m3` model, which supports Persian.

The project works in two stages:

1. **Dataset vectorization (offline step):** `vector.py` reads `companies_dataset.csv`, builds a text representation of every company profile, embeds it with `bge-m3` through Ollama, and stores the vectors in ChromaDB.
2. **Search application (online step):** the Django application embeds the user's query, retrieves similar profiles from ChromaDB, ranks them, and returns the results to the frontend.

## Features

- Persian-language focus (Persian RTL interface, multilingual `bge-m3` embeddings)
- Semantic search using vector embeddings
- Resumable dataset indexing script that skips already-indexed profiles
- Keyword-based company matching
- Hybrid scoring: keyword matching (80%) combined with semantic similarity (20%)
- Persian-aware text normalization and tokenization
- Short explanation for each top result, generated by a local LLM (Qwen2.5-3B) with an automatic rule-based fallback
- Results can also be saved as a text report (`result.txt`) when running from the terminal
- Retrieval-Augmented Generation (RAG) pipeline
- Local embedding and language model integration through Ollama (`bge-m3` and `Qwen2.5-3B-Instruct`)
- RESTful API built with Django REST Framework
- Vector storage and similarity search using ChromaDB
- PostgreSQL integration for storing search requests
- Persian, right-to-left user interface
- Responsive Persian RTL frontend built with Bootstrap 5 and vanilla JavaScript
- Docker Compose support with an Nginx configuration (`nginx.conf`)

## System Architecture

### Stage 1: Dataset Vectorization (`vector.py`)

1. **Read CSV:** `companies_dataset.csv` is loaded (UTF-8 with BOM supported).
2. **Validate:** the script checks that all required columns exist and that `id` values are unique.
3. **Build profile text:** each row becomes a text document containing name, type, description, expertise, skills, project types, experience level, location, and minimum/maximum budget.
4. **Embed:** profiles are sent to Ollama (`/api/embed`) in small batches (4 per request) using the `bge-m3` model, with retries on failure.
5. **Store:** vectors, documents, and metadata are saved in the persistent ChromaDB collection `company_profiles_bge` (`./chroma_db`).
6. **Sanity check:** a test semantic search runs at the end and prints the top 5 results.

### Stage 2: Search Application (`main.py`, exposed through Django)

1. **User Input:** The user enters a natural-language query (Persian or English) through the frontend.
2. **API Request:** JavaScript (`frontend/script.js`) sends a POST request to `/api/search/`.
3. **Input Validation:** Django REST Framework serializers validate the query; empty queries are rejected.
4. **Health Check:** The engine verifies that Ollama is reachable and that the ChromaDB collection exists and is not empty.
5. **Query Embedding:** The query is embedded with `bge-m3` through Ollama.
6. **Vector Retrieval:** ChromaDB returns the 20 nearest company profiles (`RETRIEVE_K`).
7. **Profile Parsing:** Each result is converted into a structured profile from its metadata and document text (English and Persian field names are supported).
8. **Hybrid Ranking:** Each candidate receives a keyword score and a relative semantic score; the two are combined into the final score.
9. **Explanation:** The top 5 results (`TOP_N`) get a short explanation generated by Qwen2.5-3B. If the model fails, a rule-based explanation is used instead.
10. **Response Preparation:** After a successful search the query is saved to PostgreSQL, and the backend returns structured JSON, with a warning if the best keyword score is below 25.
11. **Result Display:** The frontend displays company profiles, scores, and explanations.

The same engine can be run directly from the terminal (`python main.py`), which prints the ranked results and writes them to `result.txt`.

## Getting Started

### Prerequisites

- Python and the dependencies listed in `requirements.txt`, or a Docker environment
- Docker Compose for containerized deployment
- Ollama with the required models installed: `bge-m3` (embeddings) and `Qwen2.5-3B-Instruct` (explanations)
- ChromaDB containing indexed company profiles (`chroma_db/`)
- PostgreSQL configured for the Django application

### 1. Configure the Environment

Create a `.env` file in the project root and configure the environment variables, database connection, Ollama endpoint, and other settings according to `config/settings.py` and `docker-compose.yml`.

Ensure that the required Ollama models are available and that the company profile data (`companies_dataset.csv`) has been indexed in ChromaDB.

### 2. Vectorize the Dataset (run once, before the first search)

Pull the embedding model and make sure Ollama is running:

```bash
ollama pull hf.co/lm-kit/bge-m3-gguf:latest
ollama pull hf.co/Qwen/Qwen2.5-3B-Instruct-GGUF:Q4_K_M
```

The second model is only needed for the generated explanations (see `USE_LLM` below); the search itself works without it.

Then index the dataset into ChromaDB:

```bash
python vector.py
```

Notes about the indexing script:

- Required CSV columns: `id`, `name`, `type`, `description`, `expertise_areas`, `skills`, `project_types`, `experience_level`, `location`, `budget_min`, `budget_max`.
- The script is **resumable**: profiles whose `id` already exists in ChromaDB are skipped, so you can safely re-run it after an interruption or after appending new rows.
- Existing profiles are **not updated** when their CSV content changes. To re-index changed data, delete the `chroma_db/` directory (or use a new collection name) and run the script again.
- The first request may take around 30 seconds while the model loads into memory.
- Requests to `localhost` ignore system proxy/VPN settings (`NO_PROXY`), so Ollama stays reachable while a VPN is active.
- The embedding model, collection name, batch size, timeout, and Ollama URL are constants at the top of `vector.py`. The search application must use the same embedding model and collection name.

### 3. Start the Application

Start the services from the project root directory:

```bash
docker compose up -d
```

If the containers have already been built and configured, this command starts the services without explicitly requesting a rebuild. To rebuild the images after code changes, use:

```bash
docker compose up -d --build
```

### 4. Apply Migrations

```bash
python manage.py migrate
```

(or run the same command inside the backend container when using Docker).

### 5. Access the Frontend

Open the following URL in your browser:

**Frontend URL:** http://localhost:8080/

### 6. Search for Companies

Enter a description of your project (preferably in Persian), required technical skills, or preferred technologies in the search interface.

The system retrieves relevant company profiles, ranks the results, and displays the matching companies with their scores and profile information.

## Configuration

The search engine in `main.py` is configured through constants at the top of the file:

| Setting | Default | Description |
|---|---|---|
| `OLLAMA_URL` | `http://localhost:11434` | Ollama endpoint; can be overridden with the `OLLAMA_URL` environment variable (useful in Docker) |
| `EMBED_MODEL` | `hf.co/lm-kit/bge-m3-gguf:latest` | Embedding model (must match the one used in `vector.py`) |
| `LLM_MODEL` | `hf.co/Qwen/Qwen2.5-3B-Instruct-GGUF:Q4_K_M` | Model used to write result explanations |
| `DB_PATH` / `COLLECTION_NAME` | `./chroma_db` / `company_profiles_bge` | ChromaDB location and collection (must match `vector.py`) |
| `RETRIEVE_K` | `20` | Number of candidates retrieved from ChromaDB |
| `TOP_N` | `5` | Number of final results returned |
| `KEYWORD_WEIGHT` / `SEMANTIC_WEIGHT` | `0.80` / `0.20` | Weights of the final score |
| `WEIGHTS` | skills 30, expertise 40, project types 30 | Weights of the keyword score fields |
| `MIN_USEFUL_SCORE` | `25` | Below this keyword score for the best result, a warning is returned |
| `USE_LLM` | `True` | Enable/disable LLM-generated explanations |
| `DEBUG` | `False` | Print extra diagnostics |
| `RESULT_FILE` | `result.txt` | Output file of the terminal mode |

## API Documentation

### Search Companies

- **Endpoint:** `/api/search/`
- **Method:** `POST`
- **Content-Type:** `application/json`

#### Example Request

```json
{
  "query": "Companies specializing in Java, Spring Boot, and backend development"
}
```

#### Response Structure

The API returns a JSON object containing the submitted query, the number of results, an optional warning, and a list of up to 5 matching companies.

Example response structure:

```json
{
  "query": "شرکت متخصص در Python و Django برای پروژه وب",
  "count": 1,
  "warning": null,
  "results": [
    {
      "name": "Example Company",
      "final_score": 85.5,
      "keyword_score": 80.0,
      "semantic_score": 100.0,
      "reason": "Short explanation of why the company matches.",
      "profile": {
        "name": "Example Company",
        "type": "",
        "description": "",
        "expertise": "",
        "skills": "",
        "project_types": "",
        "experience_level": "",
        "location": "",
        "budget_min": "",
        "budget_max": "",
        "raw_text": ""
      }
    }
  ]
}
```

`warning` contains a Persian message when the best result's keyword score is below 25, meaning no strong direct term match was found and the results should be reviewed with caution.

*Note: The response above is illustrative. Actual scores, company names, explanations, and profile fields depend on the indexed data and the ranking configuration.*

#### Request Validation

The `query` field is validated by `CompanySearchSerializer`: it is required, cannot be blank, is trimmed of surrounding whitespace, and is limited to 2000 characters.

#### Error Responses

| Status | When | Body |
|---|---|---|
| `400` | Missing, blank, or too long `query` (serializer validation) | Standard DRF field errors, e.g. `{"query": ["This field is required."]}` |
| `400` | The search engine rejects the input (`ValueError`) | `{"error": "<message>"}` |
| `500` | Any other failure (Ollama unreachable, empty database, ...) | `{"error": "اجرای جست‌وجو با خطا مواجه شد."}` (details are written to the Django log) |

Only successful searches are saved to the database; failed requests are not stored.

## Frontend

The frontend is a static page (`frontend/`) written with plain HTML, CSS, and JavaScript, with no build step. The layout uses **Bootstrap 5.3.3 (RTL build)**, loaded from the jsDelivr CDN, so the browser needs internet access to load it (or the files must be hosted locally for offline use).

### Behavior (`script.js`)

- Sends the query with `fetch` as a `POST` request to the relative URL `/api/search/`, so the page and the API must be reachable from the same origin (for example through the reverse proxy configured in `nginx.conf`).
- Search is triggered by the search button only; the form's default submit is disabled. Empty queries are rejected on the client with a warning.
- While a request is running, the button is disabled and shows a loading label, and repeated clicks are ignored.
- Status messages are shown as Bootstrap alerts: info (searching), success (number of companies found), warning (empty query or the API's `warning` field), and danger (errors).
- Errors are shown to the user when the server returns invalid JSON or a non-2xx status; the message uses the response's `error` or `detail` field when present.
- All content is rendered with `textContent` (no `innerHTML`), so company data coming from the API cannot inject HTML or scripts.

### Result Cards

Each result is shown as a card (3 per row on large screens, 2 on medium, 1 on mobile) with:

- Company name and rank
- Final match score (0–100) with a progress bar
- Keyword score and semantic score
- Description, expertise, experience level, and location
- Skills and project types as badges
- Budget range
- The explanation of why the company was suggested
- The raw profile text, only when the structured fields are missing

Missing fields are skipped, and invalid scores are displayed as "نامشخص" (unknown).

## Ranking Methodology

ProjectEST combines keyword matching with semantic retrieval. All of this logic lives in `main.py`.

### Text Normalization

Before matching, text is lowercased and Arabic variants are unified with Persian (`ي`→`ی`, `ك`→`ک`, `ة`/`ۀ`→`ه`). Zero-width non-joiners, directional marks, and tatweel are removed, punctuation is stripped, and Persian and English stop words are filtered out. Tokens are extracted separately for English (e.g. `python`, `c++`, `node.js`) and Persian words.

### Keyword Score (0–100)

The query's terms are matched against three profile fields, and the score of each field is the percentage of query terms found in it:

| Field | Query terms used | Profile text searched | Weight |
|---|---|---|---|
| Skills | English terms | `skills` | 30 |
| Expertise | Persian terms | `expertise_areas` + `description` | 40 |
| Project types | Persian terms | `project_types` | 30 |

Matching is exact, or by prefix for terms of at least 5 characters (to tolerate simple word-form differences). The keyword score is the weighted average of the three field scores.

### Semantic Score (0–100)

Derived from the vector distance of each of the 20 retrieved candidates, min-max normalized **within that candidate set**: the closest candidate gets 100 and the farthest gets 0. It is therefore a *relative* score, not an absolute similarity.

### Final Score

```text
final_score = 0.80 × keyword_score + 0.20 × semantic_score
```

Candidates are sorted by `final_score`, and the top 5 are returned. The scores support relative ranking of the companies for one query and should not be interpreted as calibrated probabilities or compared across different queries.

### Explanations

For each of the top results, Qwen2.5-3B writes a two-sentence explanation based only on the profile fields and the keyword score. It is instructed not to invent information and to say so when the match is weak. If the model is unavailable or fails, a rule-based explanation (matched skills, expertise, project topics, and location) is used instead. The LLM does not influence the ranking.

### Known Limitations

- Skill matching uses English terms only, and expertise/project-type matching uses Persian terms only. A purely Persian query therefore scores 0 on skills, and a purely English query scores 0 on expertise and project types.
- Because the keyword score has 80% of the weight, results with little term overlap can rank low even if they are semantically close.
- Budget, location, and experience level are shown in the results but are not used in scoring.

## Database and Storage

### ChromaDB

ChromaDB stores vector representations of company profiles and supports semantic retrieval. The persisted store is located in the `chroma_db/` directory and is populated by `vector.py` into the collection `company_profiles_bge`. Each record stores the profile text plus metadata (`id`, `name`, `type`, `location`, `experience_level`, `budget_min`, `budget_max`).

### PostgreSQL

PostgreSQL stores search request records through the `SearchRequest` model (`matcher/models.py`): the submitted `query` text and an automatically set `created_at` timestamp. A record is created only after a search completes successfully.

## Local AI Integration

ProjectEST uses Ollama to run two models locally:

- **`hf.co/lm-kit/bge-m3-gguf:latest`**: multilingual embedding model (supports Persian) used both for indexing (`vector.py`) and for embedding queries (`main.py`).
- **`hf.co/Qwen/Qwen2.5-3B-Instruct-GGUF:Q4_K_M`**: small instruction-tuned language model used only to write the short explanation for each top result.

This approach allows the application to use locally hosted models rather than requiring a cloud-based language model API for its configured inference workflow.

The availability of the required models and sufficient system resources is necessary for successful inference. Explanations are generated one result at a time, so enabling them (`USE_LLM = True`) increases response time, especially on machines without a GPU.

## Error Handling

The API validates incoming search requests (see *Request Validation* and *Error Responses* above) and always returns structured JSON.

The search engine checks its dependencies before searching: it fails with a clear message if Ollama is unreachable, if the ChromaDB directory (`./chroma_db`) does not exist, or if the collection is empty. In the API these failures are logged with a full traceback and returned as a generic `500` error. In terminal mode, connection errors, timeouts, and HTTP errors from Ollama are reported separately. If the language model fails while generating an explanation, a warning is printed and the rule-based explanation is used.

The frontend displays status messages and error information when a request fails.

## Testing

API tests are located in `matcher/tests.py` (`CompanySearchAPITests`) and can be run with:

```bash
python manage.py test
```

The tests mock the search engine (`matcher.views.find_matching_companies`), so they do not need Ollama or ChromaDB. They cover:

- A successful search returns `200`, saves the query in the database, and calls the engine once with the query.
- An empty `query` is rejected with `400` and the engine is not called.
- A missing `query` is rejected with `400` and the engine is not called.

## Deployment Notes

- Ensure that the required services are running before performing searches.
- Verify the Ollama endpoint (`OLLAMA_URL`) and that both models are pulled.
- Confirm that `vector.py` has been run and that ChromaDB contains the expected company profiles.
- Use the same embedding model for indexing and querying.
- Apply the necessary Django database migrations.
- Configure environment variables in `.env` and database credentials appropriately.
- Verify the configured ports and service names in `docker-compose.yml` and `nginx.conf`.
- The frontend loads Bootstrap from a CDN; make sure the client has internet access or host Bootstrap locally.
- Keep `.env` out of version control (it should be listed in `.gitignore`). Do not expose database credentials or other sensitive configuration values in a public repository.
